# Покращення формування дайджесту за попередню добу

## 1) Короткий аналіз поточного підходу

Поточна логіка формування добового дайджесту має кілька технічних причин, через які вихід часто стає вузькотематичним:

1. **Вибірка не балансується між категоріями**: береться до `max_per_category` у кожній категорії, але категорії з більшою кількістю сигналів все одно домінують за загальним обсягом (бо немає загального бюджету й квот).  
2. **Сортування за категорією + score** (`ORDER BY m.ai_category, m.ai_score DESC`) призводить до «пачкового» потрапляння однотипних новин у промпт моделі.  
3. **Немає етапу кластеризації подій**: навіть при `is_dedup=0` у добу лишаються семантично схожі повідомлення (різні канали про одну й ту саму подію).  
4. **Однаковий поріг `min_score` для всіх категорій** може вибивати «рідкісні» теми, де оцінки системно нижчі, але редакційно важливі.  
5. **Провайдер отримує плаский список повідомлень** без структури «топ-події + доважок різноманіття», тому LLM природно «йде» в наймасовіші теми.

## 2) Рішення №1 (швидке): Квоти різноманіття + загальний бюджет

### Ідея
Ввести цільовий розмір дайджесту (наприклад, 18–25 повідомлень на вхід LLM) і розподілити цей бюджет по категоріях:

- `min_per_category` (наприклад 1) для всіх категорій, де є релевантні новини;
- `max_per_category` лишається «стелею»;
- решта слотів добирається за глобальним score, але з diminishing returns для уже заповнених категорій.

### Що дає
- Стабільний баланс тем у кожному випуску.
- Мінімальна інвазивність у код (переважно `get_digest_messages` + конфіг).

### Ризики
- Інколи в дайджест потраплятимуть менш «сильні» елементи заради різноманіття.

## 3) Рішення №2 (оптимальне за якістю): Подієва кластеризація + MMR-відбір

### Ідея
Перед складанням промпта пройти 2 етапи:

1. **Кластеризація в межах доби** (event-level): групуємо схожі повідомлення в події (ембеддинги + косинусна близькість, або дешевше — MinHash/TF-IDF).
2. **MMR (Maximal Marginal Relevance)** для вибору представників:
   - maximize `relevance` (ai_score, надійність джерела, свіжість);
   - penalize `similarity` до вже вибраних подій;
   - додати бонус за категорії, які ще не представлені.

### Що дає
- Значно менше повторів однієї події.
- Краща тематична широта без жорстких квот.

### Ризики
- Більше обчислень і складніша відладка.

## 4) Рішення №3 (редакційно-кероване): 2-рівневий дайджест

### Ідея
Замість одного списку подавати LLM структурований payload:

- **Core block**: топ-8/10 найважливіших подій доби (без категорійних обмежень).
- **Diversity block**: по 1–2 події з недопредставлених категорій.

У промпті явно зафіксувати формат:
- 40–50% тексту на core;
- 50–60% на diversity;
- окремий розділ «Що поза мейнстрімом».

### Що дає
- Керований редакційний баланс (не втрачаємо головні новини і не скочуємося у монодайджест).
- Можна реалізувати без повної перебудови БД.

### Ризики
- Потрібно підтримувати промпт і формат виходу дисципліновано.

## 5) Рішення №4 (джерела): Баланс за source diversity

### Ідея
Додати обмеження на кількість повідомлень від одного джерела у вхідний набір (`max_per_source`), плюс вагу довіри до джерела.

### Що дає
- Менше «перекосу» в одну сітку каналів.
- Дайджест відображає ширший інформаційний ландшафт.

### Ризики
- Якщо джерел мало, можлива втрата найякісніших оновлень.

## 6) Рекомендований план впровадження (по етапах)

### Етап A (1–2 дні, low risk)
1. Додати `target_items`, `min_per_category`, `max_per_source` у налаштування.
2. Змінити відбір у `get_digest_messages` на алгоритм квот + добір залишку.
3. Додати метрики різноманіття в `digest_items` аналітику:
   - кількість категорій у випуску;
   - HHI/entropy по категоріях;
   - частка топ-1 категорії.

### Етап B (3–5 днів, medium risk)
1. Впровадити легку кластеризацію подій.
2. Відбір через MMR з категорійним бонусом.
3. A/B порівняння з поточним алгоритмом на 7–14 днів.

### Етап C (після валідації)
1. Перехід на 2-рівневий формат (core + diversity).
2. Налаштування під різні режими (`previous_day`, `previous_24h`) окремими профілями.

## 7) Який варіант обрати зараз

Якщо потрібен **швидкий ефект без великого рефакторингу** — почати з **Рішення №1 + елементи №4**.  
Якщо ціль — **максимальна якість і мінімум повторів** — рухатися до **Рішення №2** як основи і доповнити його структурованим промптом із **Рішення №3**.

## 8) Мінімальні зміни в коді для старту

1. У конфіг дайджесту додати:
   - `target_items` (int, default 20)
   - `min_per_category` (int, default 1)
   - `max_per_source` (int, default 3)
2. Оновити `repo.get_digest_messages(...)`:
   - повертати кандидатів із полями `source_name`, `ai_category`, `ai_score`, `published_at`;
   - робити балансувальний post-processing в Python.
3. Перед `provider.generate_digest(...)` формувати структурований `messages_text` блоками за категоріями/подіями.

Це дасть помітне зниження вузькотематичності вже на першому ітераційному циклі.
